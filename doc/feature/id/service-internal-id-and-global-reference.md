# Service-Scoped Internal IDs and Global Entity References

Status: Proposed  
Last updated: 2026-10-01

## 1. Purpose

This document defines the target identity model for core `z-exchange`
entities. It separates efficient owner-service storage identity from the
globally unique reference used across service boundaries.

The central decision is:

> `internal_id` is unique within one owner service. A typed `*_ref` is the
> globally unique canonical identity used outside that service.

The distributed ID generator produces `internal_id`. A separate reference
codec produces `*_ref`.

## 2. Scope

This design applies to generated identities for core Wallet and Ledger
entities, including:

- wallets;
- wallet transactions;
- wallet reservations;
- wallet actions;
- ledger transactions;
- ledger entries; and
- ledger accounts.

It also defines how these identities are used in:

- MySQL owner and referencing tables;
- Kafka messages and partition keys;
- internal APIs;
- logs and traces;
- reconciliation; and
- analytical and big-data pipelines.

It does not redefine caller-owned idempotency keys, partner references, asset
symbols, or public/customer identifiers.

## 3. Goals

1. Keep owner-service primary keys compact and efficient for MySQL/InnoDB.
2. Allow each service to manage its ID-generator workers independently.
3. Provide one globally unique and typed reference for cross-service use.
4. Support stateless owner and logical-route discovery from a reference.
5. Keep references stable while physical shards and tables evolve.
6. Make cross-service reconciliation unambiguous.
7. Keep ID generation off the request-path network hot path.

## 4. Non-goals

1. `internal_id` is not a global identifier.
2. `*_ref` is not a customer-facing or partner-facing business identifier.
3. References do not encode an environment name.
4. References do not encode a physical database, shard, or table number.
5. References do not carry mutable business state.
6. Approximate time order from `internal_id` is not a business ordering
   guarantee.

## 5. Identity layers

| Layer | Scope | Storage | Primary use |
|---|---|---|---|
| `internal_id` | One owner service | Positive `BIGINT` | Owner PK, local joins, local lookup |
| `*_ref` | Global | `VARCHAR(64)` | APIs, messages, logs, routing, reconciliation |
| `external_id` | Public/business domain | `VARCHAR` | UI, partners, receipts, support |
| optional `id` | One table | `BIGINT AUTO_INCREMENT` | Exceptional storage-only surrogate |

### 5.1 `internal_id`

`internal_id` is the owner service's canonical machine identity. It must be
unique across:

- every entity type owned by that service;
- every concurrently running instance of that service;
- process restarts; and
- all service-owned database shards for the retention lifetime of the entity.

It may have the same numeric value as an `internal_id` generated by another
service.

A bare `internal_id` must never cross its owner-service boundary. It is valid
only with implicit or explicit knowledge of the owner service.

### 5.2 `*_ref`

`*_ref` is the canonical globally unique identity. It identifies the entity
type, carries immutable logical routing information, and contains a lossless
encoding of `internal_id`.

Examples include:

- `wallet_ref`;
- `wallet_txn_ref`;
- `wallet_reservation_ref`;
- `wallet_action_ref`;
- `ledger_txn_ref`;
- `ledger_entry_ref`; and
- `ledger_account_ref`.

Every owner entity has exactly one canonical stored reference. Existing
references are never regenerated merely because a newer reference version is
introduced.

### 5.3 `external_id`

`external_id` is optional and is created only when a customer, partner, or
support workflow needs a stable human-facing identifier. It must not expose
internal routing or storage topology.

### 5.4 Optional storage `id`

A separate auto-increment `id` is permitted only when a measured storage need
justifies decoupling the clustered key from `internal_id`. It must not be used
in APIs, messages, logs, or cross-service references.

## 6. Uniqueness model

Global reference uniqueness is compositional:

```text
globally registered entity TYPE + owner-service-unique internal_id
```

Routing fields and the checksum do not create uniqueness. They make the
reference resolvable and detect malformed input.

For example, these numeric IDs may coexist:

```text
Wallet internal_id = 123456
Ledger internal_id = 123456
```

Their references remain distinct:

```text
WTX-1-42-0-3RJ0-2NFZR6K
LTX-1-18-0-3RJ0-2Q1Q60J
```

## 7. Generator topology

### 7.1 One domain per owner service

Initial MySQL-backed generator registrations shall use separate service
domains:

```text
domain: z-exchange-wallet
generator: internal-id

domain: z-exchange-ledger
generator: internal-id
```

All generated entity types in one service share that service's generator.
Separate generators per entity type are not required.

`domain_id` and `generator_id` are generator metadata; neither value is encoded
in `internal_id`.

### 7.2 Worker allocation

One running service process acquires one leased worker from its service domain.
The generator is shared safely by all request threads in that process.

Worker IDs must be unique only within a service domain. Wallet worker `0` and
Ledger worker `0` may exist simultaneously.

The number of registered workers for a service must be at least:

```text
maximum concurrent service instances + rolling-deployment overlap
```

One registered worker is sufficient for a strict stop-then-start,
single-instance deployment. At least two are required when old and new
instances can overlap.

### 7.3 Restart behavior

A worker ID is stable for the lifetime of one active lease. It is not a stable
identity for a host, container, or logical service across restarts.

After restart, a process may acquire any available registered worker. A worker
may be reused only after the previous lease is no longer active and the
configured cooling period has ended.

The service must fail closed when it cannot prove valid worker ownership. It
must not fall back to an unleased or locally assigned worker.

### 7.4 Initial bit layout

The initial positive Java `long` layout is:

```text
1 reserved sign bit | 41 time bits | 10 worker bits | 12 sequence bits
```

This provides, per service domain:

- worker IDs `0..1023`;
- up to 4,096 IDs per worker per millisecond; and
- approximately 69 years of millisecond time range from the configured epoch.

The epoch is immutable after the first production ID is issued. It must be
recorded in the domain seed migration and operational runbook.

### 7.5 Clock and ordering contract

Generated IDs provide approximate creation-time order only. Consumers must not
use numeric order as a correctness, settlement, or event-ordering rule.

The accepted clock-skew limitation and lease cooling controls are documented in
`design/issues/z-id-generator-clock-skew-risk.md`.

## 8. Reference format

### 8.1 Version 1 grammar

Version 1 uses six hyphen-separated uppercase ASCII fields:

```text
<TYPE>-<V>-<B>-<P>-<ENC_INTERNAL_ID>-<CHK>
```

Example:

```text
WTX-1-42-202610-3RJ0-1NBTVFS
```

No field may contain a hyphen.

| Field | Meaning |
|---|---|
| `TYPE` | Globally registered entity-type code |
| `V` | Reference format and routing version |
| `B` | Owner-service logical virtual bucket |
| `P` | Immutable business partition, or `0` when unused |
| `ENC_INTERNAL_ID` | Lossless Crockford Base32 encoding of positive `internal_id` |
| `CHK` | Fixed-width Crockford Base32 encoding of the reference checksum |

### 8.2 Initial type registry

| Type | Owner | Entity |
|---|---|---|
| `WAL` | Wallet | Wallet |
| `WTX` | Wallet | Wallet transaction |
| `WRS` | Wallet | Wallet reservation |
| `WAC` | Wallet | Wallet action |
| `LTX` | Ledger | Ledger transaction |
| `LEN` | Ledger | Ledger entry |
| `LAC` | Ledger | Ledger account |

Type codes are permanent. A retired type code must never be assigned to a new
entity meaning.

### 8.3 Encoding rules

1. The canonical representation is uppercase ASCII with no surrounding
   whitespace.
2. `V` and `B` use canonical unsigned base-10 without leading zeroes.
3. `P` is `0` when the entity has no business partition. Otherwise its format
   is defined by `TYPE` and `V` and is immutable after reference creation.
4. `ENC_INTERNAL_ID` uses unpadded Crockford Base32.
5. Decoding `ENC_INTERNAL_ID` must produce a value in `1..Long.MAX_VALUE`.
6. A decoder must reject non-canonical alternative spellings rather than
   normalize and silently accept them.

### 8.4 Checksum

For version 1, `CHK` is the seven-character Crockford Base32 encoding of the
unsigned 32-bit CRC32C value calculated over the UTF-8 bytes of:

```text
<TYPE>-<V>-<B>-<P>-<ENC_INTERNAL_ID>
```

The value is left-padded with `0` to seven characters.

The checksum detects corruption and common transcription mistakes. It is not
an authentication mechanism and must not be used as authorization evidence.

### 8.5 Reference versioning

`V` selects both the parser and owner-routing rules. A new version may change
encoding or routing interpretation, but it must not invalidate existing
references.

Every deployed reader must continue decoding every version present in retained
data. New references use the currently active version for their entity type.

## 9. Reference creation

The owner service creates a reference in this order:

1. Generate `internal_id` locally from the active leased generator.
2. Select the entity `TYPE`.
3. Select the active reference version.
4. Calculate the owner-service virtual bucket.
5. Determine the immutable business partition, or use `0`.
6. Encode the reference and checksum.
7. Persist `internal_id` and `*_ref` in the same database transaction as the
   entity.

Gaps in generated `internal_id` values are acceptable. Reusing an ID is not.

The owner table's unique constraint on `*_ref` is the final database guard
against implementation defects.

## 10. Routing model

### 10.1 Owner routing

The owner service resolves physical storage using:

```text
TYPE + V + B + optional P + routing configuration
```

`B` is a logical bucket, not a physical shard number. Routing configuration may
move a logical bucket to another database or table without changing the
reference.

For each `TYPE` and `V`, the bucket function and virtual-bucket count are
immutable. The exact version-1 bucket functions must be published with the
reference codec before sharding is enabled.

### 10.2 Consumer-owned partitioning by an external reference

When a service partitions its own table by an entity owned by another service,
it must store the complete external `*_ref`.

It should derive and persist its own local logical partition bucket from that
canonical reference:

```text
consumer_bucket = consumer-defined stableHash(external_ref)
                  mod consumer_virtual_bucket_count
```

The consumer must not automatically reuse `B` embedded in the external
reference. That bucket belongs to the owner service's routing model.

Reusing the owner's bucket is permitted only under an explicit, versioned
cross-service co-partitioning contract.

The local derived bucket is an optimization. The complete external reference
remains authoritative and must be sufficient to rebuild or validate the
derived value.

## 11. Storage rules

### 11.1 Owner table

The target schema for a core owner table is:

```sql
CREATE TABLE wallet_transactions (
    internal_id BIGINT UNSIGNED NOT NULL,
    wallet_txn_ref VARCHAR(64) NOT NULL,
    external_id VARCHAR(64) NULL,
    -- business columns
    PRIMARY KEY (internal_id),
    UNIQUE KEY uk_wallet_txn_ref (wallet_txn_ref),
    UNIQUE KEY uk_wallet_txn_external_id (external_id)
);
```

Omit `external_id` when the entity has no public or business-facing identity.

### 11.2 Same-service relationship

A relationship wholly inside one owner service may use the target entity's
`internal_id` for compact joins:

```sql
CREATE TABLE wallet_actions (
    internal_id BIGINT UNSIGNED NOT NULL,
    wallet_action_ref VARCHAR(64) NOT NULL,
    wallet_txn_internal_id BIGINT UNSIGNED NOT NULL,
    -- business columns
    PRIMARY KEY (internal_id),
    UNIQUE KEY uk_wallet_action_ref (wallet_action_ref),
    KEY idx_wallet_txn_internal_id (wallet_txn_internal_id)
);
```

The corresponding `*_ref` must still be used whenever the relationship crosses
a service boundary or needs owner routing without local context.

### 11.3 Cross-service relationship

A table must never persist another service's bare `internal_id` as an identity.
It stores the external service's typed reference:

```sql
CREATE TABLE ledger_transactions (
    internal_id BIGINT UNSIGNED NOT NULL,
    ledger_txn_ref VARCHAR(64) NOT NULL,
    source_wallet_txn_ref VARCHAR(64) NOT NULL,
    local_partition_bucket SMALLINT UNSIGNED NOT NULL,
    -- business columns
    PRIMARY KEY (internal_id),
    UNIQUE KEY uk_ledger_txn_ref (ledger_txn_ref),
    UNIQUE KEY uk_source_wallet_txn_ref (source_wallet_txn_ref)
);
```

There are no database foreign keys across service-owned databases.

### 11.4 MySQL table partitioning

If MySQL native partitioning is used, every unique key must include all columns
required by MySQL's partitioning rules. The schema must be reviewed against the
exact deployed MySQL version before migration.

Partition expressions should use stored numeric routing columns. SQL queries
must not repeatedly parse the structured reference string to select a
partition.

## 12. API, message, and logging rules

### 12.1 APIs

Internal APIs expose typed `*_ref` fields, not bare `internal_id` values.
Field names must be entity-specific, such as `walletTxnRef`, rather than
ambiguous names such as `id` or `refId`.

At the owner-service boundary, an incoming reference is validated in this
order:

1. length and grammar;
2. known `TYPE`;
3. supported version;
4. canonical field encoding;
5. checksum;
6. routing configuration; and
7. entity existence and authorization.

Malformed, unknown-version, or checksum-invalid references are rejected. The
service must not guess a route or scan all shards as a normal fallback.

### 12.2 Kafka

Kafka commands and events use the relevant canonical `*_ref` as their business
identity and, when per-entity ordering is required, as the Kafka record key.

Using a reference as the Kafka key keeps messages for the same entity together
while the topic partition count is unchanged. It does not guarantee the same
physical Kafka partition after the partition count changes.

Outbox publication remains atomic with the business database transaction. This
ID design does not change the outbox or at-least-once delivery requirements.

### 12.3 Logs and traces

Structured logs use entity-specific reference fields:

```text
wallet_txn_ref
wallet_action_ref
ledger_txn_ref
source_wallet_txn_ref
```

An owner service may additionally log `internal_id` for local diagnosis, but
cross-service correlation uses `*_ref`.

## 13. Reconciliation and analytics

Reconciliation and analytical pipelines use the complete `*_ref` as the
canonical identity. They must not join records from different services using a
bare numeric `internal_id`.

On ingestion, a warehouse should preserve the original reference and may also
decode it into typed columns:

```text
entity_ref
entity_type
ref_version
owner_virtual_bucket
business_partition
internal_id
```

Parsed columns, dictionary encoding, or warehouse-local surrogates may be used
for performance. They do not replace `entity_ref` as the semantic identity.

If two datasets contain the same numeric `internal_id` but different entity
types or references, they represent different identities.

## 14. Reference codec contract

Reference encoding and decoding must be implemented once in a shared
infrastructure library. Services must not implement ad hoc parsers.

A representative API is:

```java
public interface EntityRefCodec {
    String encode(EntityRefParts parts);
    EntityRefParts decode(String reference);
}

public record EntityRefParts(
        EntityType type,
        int version,
        int virtualBucket,
        String businessPartition,
        long internalId) {
}
```

The shared library owns syntax, canonical encoding, checksum validation, and
version dispatch. Owner services own routing configuration and authorization.

The codec must not be used to branch on unrelated business behavior.

## 15. Current-system migration

The current schema uses auto-increment table IDs and string business IDs, such
as `wallet_transactions.txn_id`. The existing generator integration SPEC that
converts a generated `long` directly to a decimal string is a compatibility
pilot, not this target model.

Migration should be additive and staged:

1. Add nullable `internal_id` and typed `*_ref` columns while retaining current
   identifiers.
2. Deploy generator and reference-codec support with reads still using the
   legacy fields.
3. Generate both identity forms for new rows in one transaction.
4. Backfill existing rows with newly allocated `internal_id` values and stored
   canonical references.
5. Backfill local relationships and cross-service reference columns.
6. Switch messages, APIs, logs, and reconciliation to typed references.
7. Add `NOT NULL` and unique constraints after validation.
8. Change primary keys only in a separate, measured migration.
9. Retain legacy lookup aliases for the agreed compatibility window.

Backfill must preserve existing idempotency and transaction relationships. It
must not reinterpret caller-owned `reference_id` or idempotency columns as the
new canonical `*_ref` without an explicit field-by-field migration.

## 16. Operational requirements

Each service must expose enough information to diagnose:

- generator startup and configuration failure;
- acquired domain, generator, and worker;
- lease renewal failure and lease loss;
- ID generation failure;
- clock rollback;
- sequence exhaustion; and
- invalid or unsupported entity references.

Readiness for ID-creating operations requires an active safe generator lease.
The service must stop creating entities before lease ownership can become
unsafe.

Reference-codec configuration and the global type registry must be versioned,
reviewed, and deployed compatibly across producers and consumers.

Secrets, credentials, environments, physical shard names, and personal data
must never be encoded in a reference.

## 17. Required invariants

1. An `internal_id` is never reused within its owner service.
2. A bare `internal_id` never crosses an owner-service boundary.
3. Every generated entity has exactly one stored canonical `*_ref`.
4. Every `*_ref` round-trips losslessly to its structured components.
5. Every type code has exactly one permanent entity meaning.
6. Every owner table enforces uniqueness of its canonical `*_ref`.
7. Cross-service references persist the complete typed reference.
8. Consumer partitioning is derived from the complete external reference and
   remains owned by the consumer.
9. Physical storage topology is not encoded in a reference.
10. Existing references remain resolvable after routing changes and reference
    version upgrades.

## 18. Acceptance criteria

1. Concurrent generation from multiple JVMs in one service produces no
   duplicate `internal_id` values.
2. A process restart may acquire a different worker without changing API or
   storage behavior.
3. Wallet and Ledger may generate the same numeric `internal_id`; their typed
   references remain distinct and resolve to the correct owners.
4. All version-1 type codes pass encode/decode round-trip tests across boundary
   values, including `1` and `Long.MAX_VALUE`.
5. A one-character reference mutation fails checksum or grammar validation.
6. Unknown types and versions fail without a cross-shard scan.
7. Owner routing remains correct after remapping a virtual bucket to a new
   physical shard.
8. A consumer can rebuild its local partition bucket from the stored external
   reference.
9. Kafka command/reply correlation uses the canonical source entity reference
   and remains idempotent under redelivery.
10. Reconciliation joins Wallet and Ledger using `source_wallet_txn_ref`, not
    numeric `internal_id` equality.
11. Database constraints reject duplicate canonical references.
12. Lease loss stops new ID creation without falling back to an unsafe
    generator.

## 19. Decisions required before implementation

The following values must be fixed in migrations and versioned configuration
before production issuance:

1. the immutable epoch for each service generator domain;
2. the version-1 virtual-bucket count and bucket function per entity type;
3. which entity types use a business partition and the exact `P` format;
4. initial worker registrations for normal capacity and rolling overlap;
5. canonical error codes for invalid, unsupported, and unresolved references;
6. the legacy-ID compatibility and retirement window; and
7. whether any measured hot table retains an auto-increment storage surrogate.
