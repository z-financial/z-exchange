# Internal ID and Typed Reference Evolution

Status: Proposed | Last updated: 2026-10-10

## 1. Context

Phase one introduces managed `z-id-generator` instances while retaining string business IDs and auto-increment
storage keys. Storage identity, entity identity, caller references, and message identity therefore still use
overlapping names such as `id`, `txn_id`, and `reference_id`.

This phase separates numeric owner-row identity from references used by APIs, messages, logs, reconciliation, and
relationships. Because the system is not online, this is a clean cutover rather than a compatibility migration.

## 2. Decision and Scope

Every covered owner table shall use a generated `internal_id BIGINT UNSIGNED` primary key and one immutable,
unique, typed `*_ref`. APIs and messages expose references, never internal IDs.

Covered owners and their canonical references are:

```text
Wallet                  wallet_ref
Wallet transaction      wallet_txn_ref
Wallet reservation      wallet_reservation_ref
Wallet action           wallet_action_ref
Ledger account          ledger_account_ref
Ledger transaction      ledger_txn_ref
Ledger entry            ledger_entry_ref
Wallet/Ledger outbox    event_ref
```

The old auto-increment `id` and generated business-ID columns are removed from these owner tables. Dependent
columns, models, caches, logs, APIs, protobuf messages, and Kafka envelopes adopt typed references in the same
cutover.

BalanceSnapshot retains its existing primary key and receives no independent reference. Its references to migrated
entities still adopt the new names and values. Other supporting tables receive no identity redesign unless listed
above, but references they store to covered entities still migrate.

Caller-provided Wallet business references remain separate from generated entity references. For Wallet commands,
`wallet_txn_business_ref` within `initiator` is the single caller-owned idempotency identity; no separate
`idempotency_key` is retained. Entity references include an immutable logical routing bucket, but physical shard
topology and migration mechanics remain outside scope.
BalanceSnapshot identity, generator-version bits, diagnostic generator decoding, and Java support above
`Long.MAX_VALUE` are also outside scope. No dual fields, dual writes, backfill, or legacy reads are required.

## 3. Design

### 3.1 Identity and uniqueness

`internal_id` is generated by the owner service and unique within its configured generator domain. The current
topology maps one domain to each service, but consumers and schemas must not assume service scope is permanent.
Typed references are unique across covered entity types within one deployment environment through stable type
codes.

The database contract is `BIGINT UNSIGNED`; the current generator remains limited to `1..Long.MAX_VALUE` and Java
`Long`. Using the upper unsigned range later requires an explicit Java/JDBC representation change.

A typed reference is immutable and opaque to business code, conceptually:

```text
<TYPE>-<BUCKET>-<ENC_INTERNAL_ID>-<CHK>
```

`BUCKET` is a stable logical bucket, not a database or table number. Infrastructure maps it to the current physical
partition, so moving a logical bucket does not change existing references. References contain no environment or
physical topology. Exact type codes, bucket cardinality and width, encoding, checksum, and maximum length remain
required decisions.

### 3.2 Persistence and boundaries

Each owner row stores its primary key and typed reference with a unique constraint. A relationship to another
covered entity stores the target reference, not its `internal_id`. Entity-specific names are required in schemas
and service contracts; shorter names are allowed only inside an unambiguous typed model.

This rule also applies to relationships inside one service. An `internal_id` is the storage key of one owner table
and is only directly useful after the correct partition has already been selected. It does not identify the target
entity type or provide a stable route if related tables are partitioned differently later. A typed reference carries
both the expected entity type and the target's immutable logical bucket, remains valid when that bucket is moved to
another physical shard, and gives persistence, caches, messages, logs, and reconciliation one relationship form.
The larger relationship indexes are an accepted cost for avoiding a second internal-only identity model and future
lookup or migration ambiguity.

Wallet's `wallet_txn_ref` is carried as Ledger's `source_txn_ref` and remains the Kafka partition key. Successful Ledger
replies expose `ledger_txn_ref`. `command_id` becomes `command_ref`. Cache keys, structured logs, reconciliation,
and analytical exports use typed references.

### 3.3 Event and outbox identity

An outbox row uses generated `internal_id` as primary key and unique `event_ref` as message identity. A Wallet
request receives one `event_ref`, committed atomically with Wallet state and reused for immediate publication and
every retry.

A Ledger reply `event_ref` remains deterministic from the request `event_ref` and outcome. Redelivery reconstructs
the same value for same-intent deduplication; the reference need not encode the reply row's `internal_id`.

Retry scanning uses `(next_attempt_at, internal_id)` as cursor and index order. Non-strict insertion ordering may
defer a concurrent eligible row by one retry cycle. This latency is accepted, but repeated cycles must eventually
select every eligible row without starvation.

### 3.4 Opacity and inherited behavior

No diagnostic generator decoder is introduced in this phase. Business code must not decode internal IDs or entity
references or use their fields or ordering for routing, validation, authorization, or correctness. Only shared
identity and routing infrastructure may validate a reference and read its type and logical bucket.

Worker leasing, one generator per process, pool isolation, fail-closed ownership, clock-skew policy, sequence
handling, lifecycle, observability, and fixed dependency/layout configuration remain governed by the integration
SPEC.

## 4. Required Behavior

### REQ-1 — Complete identity cutover

Every covered owner row shall receive one generated `internal_id` and one typed reference. Old auto-increment and
generated business-ID owner columns shall be removed, and dependent code and schemas shall use the new model.
BalanceSnapshot and unlisted supporting tables retain their own identity model.

### REQ-2 — Reference boundaries

APIs, messages, logs, caches, reconciliation, analytics, and persisted relationships shall use typed references and
never expose another owner's `internal_id`. References are immutable and opaque to business code; shared routing
infrastructure may read their logical bucket. Caller business references remain separate from generated references,
and Wallet command replay is keyed by `(initiator, wallet_txn_business_ref)`.

### REQ-3 — Allocation, transactions, and idempotency

An internal ID and reference are allocated only for a new row and persist in the same transaction as that row and
required outbox data. Accepted replay returns stored references without replacements. Failure leaves no partial
mutation, completed idempotency result, or orphaned outbox row; unused IDs are accepted gaps.

### REQ-4 — Event identity and delivery

Request `event_ref` values are allocated once and reused for every publication. Reply references remain
deterministic for the same request and outcome. Database uniqueness is authoritative, publishers never replace
stored references, and polling eventually selects rows despite accepted single-cycle deferral.

### REQ-5 — Runtime safety and numeric compatibility

Existing generator ownership, fail-closed behavior, isolation, clock-skew acceptance, and operational signals
remain unchanged. Reference encoding is local and deterministic with no per-ID database call. Java/MyBatis must
round-trip the current positive `Long` range through `BIGINT UNSIGNED` without sign or precision changes. The
numeric ID remains opaque outside owner persistence.

## 5. Failure Behavior

- Generator unavailability, lost ownership, or reference-encoding failure prevents the write and follows the
  integration SPEC's rollback behavior; no fallback identity is permitted.
- A duplicate internal ID or reference rolls back the transaction and emits a high-severity signal; the application
  does not regenerate after a partial write.
- A malformed, unknown-type, or checksum-invalid reference returns a controlled validation/not-found result.
  Business code does not guess a route or bypass the codec.
- Idempotent and Kafka retries recover stored results. A cursor-deferred outbox row is selected later; persistent
  starvation is a defect. Clock skew remains accepted under the integration SPEC's mitigations.

## 6. Acceptance Criteria

### AC-1 — Schema and model coverage

Covered owner tables use generated unsigned internal-ID primary keys and unique typed references, with old owner
`id`/business-ID columns absent. BalanceSnapshot keeps its identity while entity-reference columns migrate.

### AC-2 — Boundary and relationship migration

APIs, protobuf/Kafka contracts, caches, logs, reconciliation output, and stored relationships use entity-specific
references. Cross-service flows contain no numeric internal ID, and Wallet-to-Ledger partitioning uses
`wallet_txn_ref`.

### AC-3 — Transaction and idempotency safety

Creation commits identity, reference, mutations, and outbox atomically. Replay returns original references;
allocation, encoding, and duplicate failures roll back fully without completing idempotency.

### AC-4 — Event and retry stability

Wallet publication and retries reuse the stored request `event_ref`; repeated Ledger outcomes reconstruct the same
reply reference. Cursor tests prove eventual selection of concurrently inserted eligible rows without starvation.

### AC-5 — Uniqueness and decoding boundaries

Reference tests cover every type and prove uniqueness across both service domains within one environment. Codec
round trips recover type, logical bucket, and internal ID, while business modules do not decode generated IDs or
references or depend on their fields or ordering.

### AC-6 — Runtime and numeric safety

Integration-SPEC lease, restart, multi-instance, clock-skew, and shutdown tests continue to pass. Persistence tests
round-trip `1`, `Long.MAX_VALUE`, and representative IDs through MySQL/MyBatis without sign or precision changes.

### AC-7 — Clean build and cutover

Wallet, Ledger, protobuf modules, and `common-util` compile and pass their tests. Production source and schemas
contain no legacy identity selection, compatibility path, or ambiguous cross-service `txn_id`/`reference_id` use.

## 7. Required Decisions

Before completion, record:

1. stable type codes for every covered reference;
2. logical-bucket cardinality, assignment rules, encoding width, and physical routing-map ownership;
3. encoding alphabet, checksum, and maximum length;
4. controlled errors for malformed or unsupported references;
5. Java/MyBatis mapping and range guard for `BIGINT UNSIGNED`;
6. final outbox cursor/index DDL using `internal_id`; and
7. the exact schema and protobuf rename matrix.
